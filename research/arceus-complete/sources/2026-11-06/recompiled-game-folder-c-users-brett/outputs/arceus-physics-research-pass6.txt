RESULT

The main physics wrapper's default mode still selects 1/30, independently of the runtime's corrected clock channel 1. However, the surrounding component preparation explicitly consumes the corrected elapsed time, and a second family of Havok worlds directly uses supplied elapsed time. Therefore normal visible movement is not sufficient evidence that every world/body is stepping correctly, and applying another multiplier to the shared world or integration function would affect already-variable worlds.

A useful existing cross-worker serial is world+0x5B8, equivalently StepInfo+0x88. It is initialized to zero and incremented by shared postsolve function 2F3AA70. The increment is reached through both single-threaded solve and a retained-RTTI hknpPostSolveTask in the multi-threaded path. Adding one read-only u32 field to the existing world-step log is the smallest useful next observation. This is a postsolve serial, not an integration/body count.

A. FLAG +121 / MAIN CLOCK / PACKED-WRITE AUDIT

1. Previously established selection, verified again in private 2af25b4.txt:
   - Wrapper+121 !=0 selects incoming S0; zero selects the embedded 1/30 constant.
   - Wrapper+124 multiplies the selected value.
   - 2AF2A10..2AF2A24 only checks scaled dt against 2^-23.
   - The normal path calls world preparation 2F39630, then 2F3B120 to solve.
   The wrapper itself has no fixed-cadence accumulator or every-fourth-call selection.

2. Constructor 2AFCD08 creates this wrapper with:
   - 2AFD174: STRH WZR,[X24,#0x120], clearing BOTH bytes +120 and +121.
   - 2AFD158 loads 0x3F800000 and 2AFD178 stores +124, initializing rate to 1.
   This packed write explains why a search for STRB +121 alone misses the actual default initializer.

3. Bounded writer/alias search:
   - The whole-main direct unsigned-immediate STRB +121 search has 21 hits. None identifies a write to this physics wrapper's mode byte.
   - Focused 2AE0000..2B10000 search for wider stores overlapping +120 and ADD +120/+121 found the constructor above plus unrelated fields/function objects.
   - 2AEFAE0 is a stack config store; 2AF0B80 is a filter-table store; 2B011A8 is static metadata, not the wrapper.
   - 2AF864C and 2AF8DD4 pass their object's embedded +120 function-object storage to a callback loaded from +110. 2AFB2D4 and 2AFB3F0 are destruction of the corresponding embedded function objects. These do not establish writes to physics mode.
   - 2B0B500 / 2B0B6A4 form an acquire/release lock at another object's +120, with wait object +114. This is not a demonstrated setter of the wrapper's adjacent +121 mode and +124 rate.
   - Manager+230 direct-load audit found constructor/destructor, 2AFE864 preparation, 2B00CA8 scheduler callback, and 2B06570 resource lookup. The latter calls lookup 2AF9418 using a hash; its +230 loads are not themselves mode writes.
   Limit: this is not an exhaustive alias proof. Indexed stores, generic copies, setters reached through arbitrary pointers, and configuration/deserialization cannot be excluded by these instruction-pattern searches. No reliable in-game setter or game option for +121 was found.
   Reproducible evidence: bootstrap.py / writers.txt, fields.py / fields.txt, and named private disassemblies.

4. Runtime relationship, read-only source inspection:
   arceus_clock.c's target-FPS correction replaces clock duration arguments for returns 278150C/2781540/2781574/27815A8 (channels 0..3). Its arceus_step supplies elapsed nanoseconds through X2. It does not set physics wrapper+121.
   2B00CA8 reads channel 1 record+8, converts ns to seconds, and calls 2AF25B4. Correcting that clock therefore corrects the wrapper input, but mode=0 still selects fixed 1/30 for this world.
   There is no claimed in-game dynamic-FPS flag. The relevant option is the runtime's existing SNX_ARCEUS_TARGET_FPS/main-clock substitution.

B. ELAPSED COMPONENT PREPARATION EXISTS BESIDE THE FIXED WORLD STEP

1. 2AFE864 gets clock channel 1 and computes elapsed seconds:
   - 2AFE88C..2AFE89C: calls clock virtual method with W1=1.
   - 2AFE8A0 loads clock-record+8 ns; 2AFE8B0..8C8 converts to float seconds.
   - 2AFE8B8 loads wrapper from manager+230; 2AFE8BC loads rate+124.
   - 2AFE8CC multiplies elapsed by rate, retaining the result in S8.
   This function does not test wrapper+121 and does not substitute 1/30.

2. Under the wrapper+128 lock it first invokes 2AF1E64. That function handles component state/enable transitions:
   - 2AF1EC4 loads component+7C and handles state=2 / state=4 separately.
   - State=2: 2AF1F48 loads +78, 2AF1F4C loads +79. Equal values skip transition.
   - If different, 2AF1F5C copies +79 to +78; nonzero dispatches vtable+88, zero vtable+90.
   This proves +78 is a synchronized component enable state, not a Havok "awake body count". Do not use it to claim sleeping bodies execute once every N frames.

3. 2AFE864 then queues 24-byte records containing:
   +0 component pointer; +8 float elapsed*rate (padding shares the next word); +10 pointer to manager+1F8.
   - First wrapper list (+28) has 8-byte component entries, with enabled +78 and state +7C==2 filter.
   - The corresponding records go to manager jobs +258 and +268 using 2AFFA44.
   - Second wrapper list (+48) additionally handles states 1 and 3 through 2AE38A4 / 2AE435C; enabled state=2 records go to manager jobs +260 / +270 through 2AFFD70.
   - 2B059CC and 2B05AB4 copy all 24 bytes into the vectors. No dt rescaling occurs in those copy helpers.

4. The pre-physics callbacks are now identified:
   - Constructor 2AFCD08 assigns callback 2B03604 to job+258 at 2AFDA38..40 and stores job at 2AFDAA4.
   - Callback 2B03604 loads record+8 into S0, record+0 into X0 and record+10 into X1, then tailcalls 2AD30B8.
   - Job+260 callback is 2B053B8, assigned at 2AFDB94..9C and job stored at 2AFDC04.
   - 2B053B8 performs the same argument extraction then tailcalls 2AE27B8.
   - Constructor establishes job+260 depends on +258 at 2AFDC70..7C; physics job+250 depends on +260 at 2AFDD00..0C.
   Thus these elapsed component callbacks precede the physics job in the known graph.

5. Concrete downstream dt usage, rather than merely observing a stored record:
   a. 2AD30B8 preserves incoming dt in S8 at 2AD30DC. In one valid-target branch it computes S8=1/dt at 2AD375C..60, passes it to 2FF5650 at 2AD3EF8..3F00, then sends two output vectors to the object's world/body pair using world vtable+190 at 2AD3F04..1C.
      2FF5650 saves the scalar at entry and multiplies its linear output vector by that scalar at 2FF5830..40; angular output also uses the scalar at 2FF5A5C..68. This is consistent with target-transform-to-velocity preparation. It is not proof that the player follows that branch in the test.
   b. 2AE27B8 preserves incoming dt at 2AE27D8, builds a step record with it at 2AE2FCC..D4, and calls 2AE3150 at 2AE3004 or 2AE3044.
      2AE3150 checks enabled +78 and state +7C==2 at entry, gates dt>2^-23 at 2AE31A0..B0, stores dt to component+478 at 2AE31D4, computes inverse dt at 2AE3200, and stores it at +47C at 2AE3238.
      It passes this structure (X1=component+470) to 2FECB8C at 2AE32BC. The library routine retains the profiling string "TtcheckSupport".
   These observations establish two independently elapsed-aware component paths. They do NOT establish all dynamic body trajectories or compensate fixed 1/30 in general.

D. SHARED WORLD POSTSOLVE SERIAL: INITIALIZATION, ORDER, AND CAUTIONS

1. world+5B8 is StepInfo+88:
   - World ctor 2F28830 forms X24=world+530 at 2F2896C, passes it as X0 and calls 2F3E870 at 2F28990.
   - 2F3EA04: STR WZR,[X0,#0x88] initializes this exact field to zero.
   - Shared 2F3AA70 keeps input world in X19. At 2F3AC64 it loads W8=[X19+5B8], increments W8 at 2F3AC68 and stores it at 2F3AC6C.
   - The increment occurs after its command/contact-cache dispatch and before simulation-context clearing and world+808 completion state. It is not the very end of the function, and entry/return alone is not the exact increment point.

2. Both solve implementations reach this function:
   - Single solve 2FE2604 calls 2F3AA70 at 2FE3068 after the inline solve/integration path (pass4 evidence).
   - Multi constructor 2F8DB0C installs a task with vtable41B3C98, adjusted interface41B3CE0, into simulation+6C0 at 2F8DD78..AC.
   - RTTI object41B3D18 has name pointer41B3D20->39A3D7C, string "17hknpPostSolveTask".
   - Its adjusted virtual execute slot41B3CF8 is 2F94354. This subtracts0x20 and tailcalls2F94000.
   - 2F94000 uses task+28 world to acquire a worker context from world+908, handles pending full-cast work from simulation+6B8, and tailcalls2F3AA70 at2F9411C.

3. Graph ordering evidence:
   - 2F9158C creates the full-cast task (simulation+6B8) at2F92420..34, records its ID at graph+4DC, and appends edge [graph+4DA, full-cast-ID] at2F92474/78.
   - It sets postsolve task+28=world and +30=simulation at2F9247C..8C, appends postsolve task to graph at2F924CC..E4, records ID atgraph+4E0, and appends edge [full-cast-ID, postsolve-ID] at2F92514/18.

   - This supports the intended dependency ordering: integration-related graph work -> solver completion point -> full casts -> postsolve. I did not re-derive the complete generic task executor or every graph-import branch in this pass; it is not a proof that every possible malformed/error/reentrant path serializes identically.

Interpretation requirements:
 - This probe is after collision/task preparation at2F39630, before the two known callers call2F3B120 for this step. The serial is normally the number of previously completed postsolve increments, not confirmation the just-prepared step has integrated.
 - Only interpret primary-world serial with alternate_world=0. The alternate-world branch can own different data.
 - Compare unsigned modular differences within the same tracked world/simulation lifetime. A counter decrease may be wrap/reset; changed simulation pointer or world reuse starts a new segment. Even an unchanged address/pointer can theoretically be reused, so also consider observed discontinuity and constructor lifetime evidence.
 - Sampling is every300 calls globally across all worlds. A count delta is not that particular world's call count. Serial delta/time delta can estimate that world's postsolve rate across a stable sampled interval; it does not yield every individual step's dt sum when dt varies.
 - A serial increment is not a body/substep/integration-range count. A valid solve can have zero active motions. It does not show which body the player uses or whether a body's velocity was externally overridden.

If a later2F269E0 integration-range hook is approved, capture serial fromsolverInfo+10->StepInfo+88 (or guardedctx+8 world+5B8), worldidentity, simulationidentity, signedW2start andsignedW3count atentry beforeoriginal. F. WHAT EXPLAINS NORMAL MOTION, AND WHAT IS STILL UNKNOWN

Established: elapsed component inputs coexist with a fixed-step main world; some components generate velocity-like outputs using1/dt; support-query components carrydtandinverse; separate transform-coupled worlds already useelapsed time. These are concrete mechanisms allowing visible movement/animation to appear normal while a differentworld's free dynamics could still be wrong.

Not established: which component/world owns player locomotion, whether every motion in the fixed world is integrated each render, how often active ranges are nonempty, and whether a particular thrown ball/body is dynamic or externally driven. Sleeping/static bodies and transform overrides make wrapper-count inference insufficient. There is no basis for a blanket correction from current static evidence.

Best next measurement after scalar serial: estimate primaryworld postsolve frequency fromstable serial samples; if it tracks120Hz withdt1/30, then capture actual integrationrange execution and a small trackedmotion cohort before decidingwhether/how to activate mode+121. Keep already-variable secondaryworlds out of that experiment.
