Mechanism verified during the read-only run:
- The main loop calls the four clock-mode updates each frame with mode 1. Their indexed setter receives 33,333,334 ns.
- Calls return to main+0x278150C, +0x2781540, +0x2781574 and +0x27815A8 for channels 0 through 3.
- The loop separately resets channel 2 to zero at main+0x2781358. Consumers check for zero before scheduling work.
- Live consumers read these duration records. This confirms they are used during execution, rather than merely dormant constants.

Implemented experiment:
- Full 32-byte main build ID and the three hook entry instructions must match before anything is installed.
- Only the four observed call sites and their expected 33,333,334 ns input are eligible for replacement.
- Channel 0 samples elapsed host time since the previous batch. Channels 1 through 3 use that same duration.
- Zero-duration writes and other call sites are unchanged. Long stalls are capped at 100 ms; excess time is intentionally discarded, so this does not claim time conservation through long loads/stalls.
- Runtime presentation cap becomes 60 for this process only. The INI default and nvn_native=0 remain.
- No Z-A implementation was copied. This uses Arceus's verified duration setter, not Z-A addresses or its integer tick algorithm.
